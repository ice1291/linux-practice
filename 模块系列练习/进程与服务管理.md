# 进程与服务管理
## systemctl:linux系统（systemd）下管理服务的核心命令
	systemctl status/start/stop/restart/enable/disble 服务名

## ps -ef / ps aux ：查看当前系统里所有正在运行的进程列表
运维看点：-ef 和 aux 都是显示全量进程，但输出格式略有不同。配合 grep 可以精准定位某个进程，比如 ps -ef | grep nginx。


## kill/pkill/killall：向进程发送信号，通常用于停止进程
kill <PID>：默认发送 SIGTERM（15）信号，这是优雅退出，告诉进程“请收拾好手头的工作再下班”。
kill -9 <PID>：发送 SIGKILL（9）信号，这是强制击杀，内核直接干掉进程，不给任何清理资源的机会。运维大忌：不到万不得已（比如进程卡死无响应），绝不用 -9！


## lsof -i :端口追踪，列出打开的文件（List Open Files）。加上-i可以查看网络连接和端口占用
运维看点：服务启动失败，提示“Address already in use”（端口被占用）时，用 lsof -i :80 就能立刻揪出是谁霸占了 80 端口。


# 实战

场景 1：服务启动失败排查
你刚修改了 Nginx 的配置文件并执行了 systemctl restart nginx，但发现服务没起来。
任务：请写出一条命令，查看 Nginx 服务的当前运行状态以及系统记录的最近报错日志。
systemctl status nginx
journalctl -xeu nginx。这条命令会调出 Systemd 的完整日志，并且自动过滤出 Nginx 相关的报错，是深度排障的神器。

场景 2：精准定位“僵尸”进程
开发反馈说有一个 Python 脚本卡死了，进程名叫 data_sync.py，但不知道它的 PID 是多少。
任务：请写出一条命令，从所有进程列表中过滤出包含 data_sync.py 的进程，并显示它的 PID。
ps -ef | grep data_sync.py

过滤自身：用 grep 过滤时，经常会把 grep 命令本身也搜出来。你可以用 grep -v grep 把它排除掉。
更优雅的写法：在 grep 中，你可以把关键字的第一个字符放进方括号里，比如 ps -ef | grep [d]ata_sync.py。因为正则表达式 [d]ata_sync.py 依然能匹配到 data_sync.py，但 grep 命令自身的进程列表里写的是 [d]ata_sync.py，所以就不会匹配到自己了。这是运维老手常用的技巧！

场景 3：端口冲突排查
你准备启动一个 Tomcat 服务（默认 8080 端口），但提示端口被占用。
任务：请写出一条命令，查看到底是哪个进程占用了 8080 端口。
ss -tunlp | grep 8080 或 lsof -i | grep 8080
如果想更精准一点，可以加上 :，写成 ss -tunlp | grep :8080，防止误匹配到 PID 为 8080 的进程。

场景 4：优雅地停止服务
你确认了场景 2 中卡死的 Python 脚本的 PID 是 12345。
任务：请写出先尝试优雅停止该进程的命令。如果 10 秒后它依然卡死，再写出强制杀死它的命令
kill 12345 ,kill -9 12345

在实际生产环境中，执行 kill 12345 后，我们可以用 sleep 10 等 10 秒钟，然后再检查进程是否还在。如果写成一条自动化脚本，可以这样：kill 12345 && sleep 10 && kill -9 12345
